# Codex 接力开发文档编写指南

## 1. 文档目的

本文档总结本轮对话中关于“如何为一个已有项目建立详细文档，以指导新的 Codex/AI 进行自主循环开发”的方法论、规则和文件体系。

这份文档不是针对“一览”这个具体产品本身，而是针对另一个已有项目时，如何为它建立一套可交接、可持续、可自主推进的 AI 开发文档系统。

目标是让一个没有上下文、没有历史记忆的 Codex，在进入项目后，仅凭固定提示词和仓库内文档，就可以：

- 恢复当前项目状态
- 找到当前最应该做的任务
- 不偏离原始用户需求
- 逐步推进开发
- 持续更新状态
- 稳定交接给下一个 Codex

## 2. 核心原则

### 2.1 原始需求文档优先级最高

无论后续设计文档、任务拆解、TODO 如何演化，AI 每轮开始前都必须重新阅读用户最初写的需求文档。

原因：

- 防止长期开发中路线逐渐漂移
- 防止 AI 只围绕现有 TODO 自证完成，而忘记产品原意
- 当设计文档和需求文档冲突时，以原始需求文档为准

适用于新项目时，应始终保留一份：

- 用户原始需求文档
- 需求冻结版或优先级说明

并在所有接力规则中明确要求 AI 每轮开始前先回读它。

### 2.2 必须有固定提示词，但提示词不能承载全部状态

固定提示词的作用是约束 AI 的工作方式，而不是承载项目状态本身。

固定提示词应只负责规定：

- 去哪里读文档
- 以哪些文件为准
- 如何选择任务
- 如何更新状态
- 如何处理阻塞
- 如何提交代码

项目的真实状态必须落在仓库文档里，而不是靠提示词临时描述。

### 2.3 必须把“状态”和“计划”分开

一个常见问题是把计划、现状、交接说明都写在一个文件里，长期下来必然混乱。

应明确拆分：

- `ROADMAP`：固定开发路线
- `TODO`：任务列表
- `STATUS`：当前真实状态
- `HANDOFF`：最近一轮交接说明
- `DECISIONS`：不可再猜测的已确认决策
- `ACCEPTANCE`：最终验收标准

### 2.4 开发路线必须符合架构依赖，而不是按页面名称平铺

如果项目采用 `MVVM`、分层架构、Clean Architecture 或类似结构，开发路线不能简单写成：

- 先主页
- 再列表页
- 再设置页

因为这样会诱导 AI 直接堆页面。

更合理的路线应按依赖展开，例如：

1. 应用壳层 / Shell
2. Domain
3. Infrastructure
4. Application
5. Presentation
6. Platform Integration
7. QA / Release

这样做的好处：

- 页面不会提前侵入数据层和业务规则
- 复杂规则能在 UI 之外单测
- 新 AI 更容易判断哪些依赖已经满足

### 2.5 文档必须能支撑“无记忆接力”

文档设计时要默认：

- 新 AI 不知道之前做了什么
- 新 AI 不知道当前在哪个阶段
- 新 AI 不知道哪些文件才是可信状态

所以文档必须让 AI 进入仓库后能回答这几个问题：

- 当前阶段是什么
- 当前里程碑是什么
- 已完成了什么
- 正在做什么
- 下一步唯一优先任务是什么
- 该任务完成标准是什么

如果文档不能让 AI 明确回答这些问题，这套文档体系就是不合格的。

## 3. 推荐文档体系

对于一个已有项目，建议在仓库中建立 `docs/` 目录，并至少包含以下文件。

### 3.1 必备文件

- `docs/AI-START-HERE.md`
  - 新 AI 的唯一入口
  - 规定读取顺序
- `docs/AI-MASTER-PROMPT.md`
  - 固定提示词正文
- `docs/PROJECT-ROADMAP.md`
  - 固定开发路线
- `docs/PROJECT-TODO.md`
  - 最小任务项清单
- `docs/PROJECT-STATUS.md`
  - 当前真实状态
- `docs/PROJECT-HANDOFF.md`
  - 最近一轮交接结果
- `docs/PROJECT-DECISIONS.md`
  - 已确认决策
- `docs/PROJECT-ACCEPTANCE.md`
  - 验收标准
- `docs/PROJECT-FILE-MAP.md`
  - 关键文件和目录地图
- `docs/PROJECT-CHANGELOG.md`
  - 按轮次记录文档和结构变化

### 3.2 业务文档

- 原始用户需求文档
- 总设计文档
- 开发任务拆解文档

这些文档继续保留，但在接力模式下，执行顺序和当前任务应以 `ROADMAP / TODO / STATUS` 为准。

## 4. 文件职责建议

### 4.1 AI-START-HERE

作用：

- 明确新 AI 的第一步做什么
- 规定文档读取顺序
- 明确开始前必须检查什么

建议内容：

- 先读固定提示词
- 强制重读原始需求文档
- 再读状态、交接、TODO、路线、决策、验收
- 开始前检查 git 状态

### 4.2 AI-MASTER-PROMPT

作用：

- 作为每次输入给新 AI 的固定提示词

建议内容：

- 明确以哪些文件为准
- 明确只做依赖已满足的最小任务项
- 明确工具链缺失时先自行安装
- 明确每完成一个最小任务项都要更新状态文档
- 明确每完成一个最小任务项都要创建一次 git commit
- 明确项目最终完成后要推送远端

### 4.3 PROJECT-ROADMAP

作用：

- 定义不可随意更改的大路线

建议内容：

- 阶段编号和名称
- 每阶段入口条件
- 每阶段必须产出
- 每阶段退出条件
- 里程碑划分

关键要求：

- 必须按真实架构依赖组织
- 不要只按页面名称粗暴排列

### 4.4 PROJECT-TODO

作用：

- 存放真正要执行的最小任务项

每个任务项建议包含：

- Task ID
- Title
- Phase
- Depends On
- Status
- Goal
- Implementation Notes
- Done When
- Verification
- Files Expected

关键要求：

- 必须拆到“可以单独完成并单独提交”的粒度
- 不能只有阶段名，没有最小任务项
- 任务依赖必须清楚

### 4.5 PROJECT-STATUS

作用：

- 记录当前客观状态

建议内容：

- 当前阶段
- 当前里程碑
- 已完成任务 ID
- 正在进行任务 ID
- 下一个唯一优先任务 ID
- 当前阻塞
- 最近验证结果
- 当前真实状态摘要
- 风险与偏差

关键要求：

- 只写“现在是什么”
- 不写大段计划

### 4.6 PROJECT-HANDOFF

作用：

- 让下一个 AI 快速接手

建议内容：

- 本轮目标
- 本轮完成
- 本轮未完成
- 当前阻塞
- 已更新文件
- 下一步唯一推荐动作
- 接手 AI 注意事项

### 4.7 PROJECT-DECISIONS

作用：

- 记录不该被后续 AI 再次猜测的结论

适合记录：

- 技术栈
- 架构顺序
- 同步策略
- 登录方式
- 平台优先级
- 不做的能力
- 提交粒度
- 开始前 git 检查

### 4.8 PROJECT-ACCEPTANCE

作用：

- 防止 AI 只完成 TODO，却没有达到原始需求

建议内容：

- 全局完成定义
- 各里程碑验收
- 最终需求映射验收

关键要求：

- 必须覆盖原始需求里的硬要求
- 不要只写“主流程可用”这种模糊词

## 5. 建议的固定规则

为保证 AI 能稳定自主循环开发，建议在文档中明确以下规则。

### 5.1 每轮开始前的强制动作

- 重读原始需求文档
- 检查 git 仓库状态

git 检查至少包括：

- 是否已经初始化 git
- 当前工作区是否有未提交改动
- 当前分支
- 是否配置远端

### 5.2 工具链缺失时的处理

不要把“缺少工具链”默认当作阻塞。

更合理的规则是：

- 先尝试自行安装或补齐环境
- 只有安装后仍无法继续，才标记 `blocked`
- 安装了新工具后，要在交接和变更记录中写明

### 5.3 每完成一个最小任务项就提交一次

这点非常重要。

建议明确要求：

- 每完成 `PROJECT-TODO.md` 中的一个最小任务项
- 先更新状态文件
- 再创建一次 git commit
- commit message 必须包含任务 ID

这样做的好处：

- 代码变化与任务边界对齐
- 后续 AI 容易回溯
- 用户容易审查每个任务的落地结果

### 5.4 不要在文档里强行规定对话何时结束

本轮对话最后明确的结论是：

- 文档中不要规定 AI 在一段对话里何时结束输出
- 由 AI 自己根据任务和阻塞情况决定

也就是说，文档应规定：

- 怎么选任务
- 怎么更新状态
- 怎么提交

但不规定：

- 做完一个任务就必须停
- 或必须一直做到全部任务结束

这种结束时机交给执行中的 AI 自主判断更合理。

## 6. 为已有项目编写这套文档时的推荐顺序

如果你要让一个新的 Codex 为“另一个已有项目”建立这套文档，推荐顺序如下：

1. 找到并固定原始需求文档
2. 写或整理总设计文档
3. 确认项目架构方式，例如 MVVM、分层架构、服务端边界
4. 建立 `docs/` 文档体系
5. 先写 `ROADMAP`
6. 再写 `TODO`
7. 再写 `STATUS`
8. 再写 `DECISIONS`
9. 再写 `ACCEPTANCE`
10. 最后写固定提示词和入口文件

不要一开始就只写提示词而不写状态体系。

## 7. 给新的 Codex 的任务目标建议

如果你以后要让新的 Codex 去给另一个项目搭这套体系，可以把目标说成：

- 阅读已有项目代码和现有文档
- 找出当前真实状态
- 找出原始需求来源
- 按项目当前架构重建开发路线
- 建立 `docs/` 接力文档体系
- 编写固定提示词
- 明确提交规则、环境补齐规则、git 检查规则
- 让后续无记忆 AI 能仅凭文档接力开发

## 8. 一个合格结果应满足什么

如果这套文档写得合格，一个新的 Codex 进入项目后，应该能做到：

- 不需要额外背景说明
- 不需要人工重新解释项目目标
- 不需要靠上下文记忆恢复状态
- 能知道先读什么、再读什么
- 能知道下一步做什么
- 能知道做完后怎么更新状态
- 能知道什么时候该 commit
- 能知道最终怎么验收和推送

如果做不到这些，说明文档还不够完整。

## 9. 建议直接复用的规则清单

以下规则适合迁移到其他项目：

- 每轮开始前必须重读原始需求文档
- 每轮开始前必须检查 git 状态
- 路线必须按真实架构依赖组织
- 任务必须拆成最小任务项
- 每个最小任务项完成后都要更新状态文档
- 每个最小任务项完成后都要 git commit
- 工具链缺失时先自行安装
- 只有安装失败后才允许阻塞
- 最终完成后必须 git push，若仓库条件未就绪则记录阻塞
- 文档中不规定 AI 对话结束时机

## 10. 最终建议

对于另一个已有项目，不要直接复制“一览”项目的业务内容，但可以直接复用这套方法：

- 同样的文档体系
- 同样的接力规则
- 同样的 git / commit / 环境处理方式
- 同样的“原始需求优先”原则

需要替换的只有：

- 原始需求文档内容
- 技术栈和架构方式
- 实际路线与阶段划分
- 具体 TODO 和验收项

如果替换完这些内容，新项目里的文档仍然能让一个无记忆 Codex 顺利接手并持续推进，那么这套文档体系就算成功。
